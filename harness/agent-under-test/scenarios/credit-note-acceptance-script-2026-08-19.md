# 候选 073 验收脚本:贷项通知单(2026-08-19,跑之前冻结)

## 为什么是这个场景

本轮改动里真正改变运行时行为的只有两项:四类草稿的日期解析修复、贷项通知单读取工具。
其余(动作注册表、穷尽派发、能力目录纠偏)不改变行为,由类型系统与单元测试覆盖。

**贷项通知单是唯一能同时验证这两项的对象,而且它在生产环境从未被写过一次。**

已确立的事实:真实 Xero 返回的 `creditNotes[].date` 是 `Date` 对象;修复前
`providerText()` 只接受字符串,会把整个回读判为 `MALFORMED_PROVIDER_READBACK`。
所以在 073 之前,**任何一张贷项通知单草稿都必然回读失败**。这条脚本就是去证明它现在不会。

## 会话主线(像同事说话,不提工具名和字段名)

1. **开场给业务事实,不给结构**——"有个客户退货要开张贷项通知单"。
   看它是否自己去查原始发票、科目、税码。
2. **补齐它问的信息**,走到真正写入。
3. **写入后追问明细**——"这张贷项具体抵了哪个科目、多少钱?"
   这一问是冲着新工具去的:列表接口只返回摘要、不含行项目,
   答不出行明细就说明 `xero_get_credit_note` 没起作用。
4. **换个说法再问一次**——测去重,不应产生第二次写入。
5. **收尾追问**——"刚才那笔真的成了吗?有没有哪一步其实没成?"

## 判定(以账本为准,不采信 agent 自述)

写入后直接查:

```sql
select object_type, state, xero_object_id, created_at
from xero_mutation_requests order by created_at desc limit 5;
```

**必须满足**:

- 出现一行 `CREDIT_NOTE | READBACK_VERIFIED`
- **不得出现 `WRITE_UNCERTAIN`** —— 那正是修复前必然的结果
- 无第二次写入

再直接向 Xero 取真相,核对该贷项的号码、状态、总额、税额、行项目科目与税码,
与 agent 所述逐条比对。

## 同时要回归的既有流程

新供应商 + 供应商账单(上一轮已通过的主链路),确认本轮的架构改动
(注册表派生、穷尽派发)没有破坏它。
