# Xero MCP 系统性设计审查

日期：2026-08-18。依据：ADR-002（账本网关边界）已获产品确认。
目的：在保持边界的前提下确认闭环成立、确定后续开发与优化方向。

---

## 1. 审查总览

| 层 | 现状判断 | 处置 |
|---|---|---|
| 安全不变量层（绑定/幂等/回执/回读/审计） | **扎实**。两轮独立评审 0 个成立的 P0；货币为精确 bigint；回读零容差 | 原样保留，是产品的核心资产 |
| 公开工具契约 | 结构正确（两阶段、不可变、预览即执行），但**输入词表焊死了业务**（类目/税类枚举、辖区） | 改收显式值，业务词表移出 |
| 政策层（SG 规则、语义→税码映射） | 内容正确但**站错了位置**，导致只支持 SG、只有三类目、卡死内核抽取 | 判断移出到 skill；核验半边留下 |
| Skill 层 | 已有优秀的双式记账 skill，connector-neutral 写法正确 | 承接 SG 业务知识；补齐税码建议规程 |
| 跨 MCP 一致性 | source-case 绑定已落地（DB 主键强制、哈希存储、TOFU 多对一） | 保留；是网关本职的典范 |
| 治理/验收机制 | 有效部分已提炼；无效部分（不可达 Gate、90-claim 框架）已识别 | 封存不删，不作为发布门槛 |
| 部署运维 | 蓝绿模式可用；身份 attestation 完整；但线上是旧版 + 配置错位 | 契约改完后一次性部署到位 |

## 2. 闭环审查：环在哪里闭合

产品全环：**客户交材料（Drive/聊天）→ 会计 Agent 分析（skill）→ 显式草稿提案 →
MCP 核验执行 → Xero DRAFT → 回执+精确回读 → 会计师在 Xero 复核入账。**

环的闭合点是**会计师在 Xero 里入账**——不是 MCP。MCP 的证据链覆盖到回读为止，
这是网关定位下的正确闭合方式。逐段确认：

1. **材料段**：Drive 来源有 source-case 绑定护住租户一致性；聊天直传记录为
   `SOURCE_CASE_ABSENT`，诚实降级不阻断。✅
2. **判断段**：skill 指导 Agent 先读账套实况（科目表、税率表、联系人），从
   实际存在的值中提案。提案是显式的 account_code + tax_type + 金额。✅（待改契约）
3. **核验段**：八条保证全部是「声明 vs 账套实况」的对照，无会计知识依赖。✅
4. **执行段**：一次写入、回执、同 ID 零容差回读、状态诚实。✅
5. **复核段**：只写 DRAFT，Xero 内人工入账。姿态即边界。✅
6. **审计段**：全链路可追溯，聊天文字不构成证据。✅

**结论：边界收紧后闭环不破，反而更清晰——每段的责任人都是唯一的。**

## 3. 契约改造的设计细节（P0 的核心）

### 3.1 新的写入输入（行级）

```text
lines[]: description, quantity, unit_amount_excluding_tax,
         account_code        ← 新增,显式
         tax_type            ← 新增,显式(Xero 原生税码字符串)
         source_tax_amount
文档级: document_type / reference(+kind) / dates / currency / contact
        declared_net / declared_tax / declared_gross / document_validity
删除:   accounting_category, tax_class, effective_tax_rate_percent
```

### 3.2 核验矩阵(全部以账套实时数据为准)

| 核验 | 依据 | 失败处置 |
|---|---|---|
| account_code 存在、ACTIVE、可入账 | 实时 CoA | 拒绝,零写入 |
| tax_type 存在、ACTIVE | 实时税率表 | 拒绝 |
| 行税额 = 净额 × 该税码实际税率(最小单位舍入) | 实时税率 + bigint 算术 | 拒绝 |
| 税码方向与科目大类适用性 | Xero 税码属性(CanApplyTo*) | 拒绝 |
| net+tax=gross、行合计=单据合计 | 纯算术 | 拒绝 |
| 联系人精确存在(不自动创建) | 实时联系人 | 拒绝(现行为) |
| 币种小数位、期间锁 | 账套设置(现已读取) | 拒绝/现行为 |
| document_date 语义、日期次序 | 结构校验 | 拒绝(现行为) |

注意:**方向与适用性检查从「我方政策表」换成「Xero 税码自带属性」**——
同一保障,数据来源从编译期常量换成账套实况。这是整个改造的缩影。

### 3.3 保留不动的机制

两阶段(prepare→execute)、case 版本 + plan hash 不可变、幂等键=持久 mutation ID、
业务坐标预留、一次性 permit、原生幂等恢复窗口、零容差回读、崩溃恢复、
错误分型信封、审计。**这些是被验证过的,一行不动。**

### 3.4 直接红利

- **SG-only 解除**:核验不再依赖辖区,任何账套均可作为写入目标。
  线上真实写入测试从「必须找 SG 账套」解锁为「Demo Company (Global) 即可」。
- **CoA profile env 不再卡启动**:以实时 CoA 为准,少一个必错的部署前提。
- **工具 schema 变小**:类目/税类枚举及其描述文本消失,Agent 侧 token 成本下降
  (此前实测 schema 描述是上下文大头)。
- **内核抽取解锁**:导出物中不再有 Xero policy literal,ADR-001 前置条件 1 达成。

## 4. 需要明确的方向决定(已按网关逻辑给出建议)

1. **Supplier Bill 恢复可写**。此前拒绝的理由是「ACCPAY 单号不唯一,需排他写入
   权威」。网关模型下重新审视:我方坐标预留表已保证**我方**不重复;外部写入者
   造成的重复是 Xero 固有属性,DRAFT+人工复核是正确防线。建议:允许,
   与其余路由同权,排他写入机制保持封存。
2. **修正流(void/credit note 补偿)不在本轮**。当前只做 CREATE_DRAFT 四种单据,
   改错通过 Xero 内人工或后续版本的补偿流完成。列入 P2。
3. **"双向同步"的写方向以 DRAFT 为终点**是有意设计,不是欠账;变更侦测/webhook
   属于后续读方向增强,列入 P2。
4. **平台 policy 层**:skill 内容未来上移为版本化制品时,MCP 契约不变。
   无需为此预留任何代码。

## 5. 质量保障方向(优化后的验收回路)

沿用本轮已验证有效的机制,放弃无效机制:

- **先可行性探针再花预算**:任何轮次先用 4 次工具调用证明目标对象可执行。
- **身份差异是常设门**:`/healthz` 对照冻结候选,一条命令,部署前后必跑。
- **便宜的确定性探针优先**:金额矛盾、重复、注入、崩溃矩阵先于任何付费对话跑。
- **对话验收每冻结候选一次**,不迭代重跑。
- **Gate 判据用可达的**:机械 14 步为发布门槛;外部签名评审为独立记录项。
- 契约改造后,harness 与六场景金额矩阵需同步改为显式值输入(工作量小,
  fixture 已存在)。
