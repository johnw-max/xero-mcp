# 系统性审查协议

用于对本仓库做根源性审查。设计目标只有一个:**让"假装查过"在机器层面不可能通过**。

审查报告最常见的失效不是结论错,是覆盖面被悄悄缩小而读者看不出来。本协议把
"查了什么"变成可机器核对的产物,而不是散文里的一句话。

---

## 一、三种已实际发生的偷懒形态(协议针对它们设计)

1. **从形状不符的样本泛化。** 一份捕获用的调用形状与生产不同,据此得出"严重
   生产缺陷";实际打一次真实接口就推翻了。
2. **未跑而报"其余通过"。** 报告里"其他都没问题",而那部分根本没有执行过。
3. **未验证的因果断言。** "移除这一步后两个红灯测试就消失了"——没有跑过,而事实相反。

三者的共同点:**结论没有证据等级,沉默无法区分"查过没问题"与"没查"。**

---

## 二、强制产物(缺一份即报告作废)

每个审查区块必须在 `artifacts/system-review/<区块>/` 下产出三份文件。

### 1. `enumeration.json` —— 范围枚举

审查开始前先枚举全部范围,**由命令产出,命令原文必须写进文件**:

```json
{
  "area": "provider-layer",
  "enumerated_by": "grep -rln 'export function' src/providers/ | sort",
  "command_output_sha256": "…",
  "items": [
    {"id": "src/providers/xeroProvider.ts", "kind": "file"},
    …
  ],
  "item_count": 42
}
```

**禁止手写 items。** 必须来自可复现的命令,任何人重跑都应得到同一份清单。

### 2. `coverage.json` —— 逐项判定

`enumeration.json` 里的**每一个** item 必须在此出现,一个不漏:

```json
{
  "area": "provider-layer",
  "verdicts": [
    {
      "id": "src/providers/xeroProvider.ts",
      "verdict": "SOUND | FINDING | NOT_EXAMINED",
      "evidence_class": "EXECUTED | READ | INFERRED | UNKNOWN",
      "evidence": "跑了 X,输出为 Y / 读了 12-48 行,该函数…",
      "finding_ids": ["PL-003"]
    }
  ]
}
```

- `NOT_EXAMINED` **是允许的**,但必须说明为什么没查。**隐瞒未查比承认未查严重得多。**
- `evidence_class` 定义:
  - `EXECUTED` —— 我运行了它,报告里有真实输出
  - `READ` —— 我读了具体行号的代码,并复述了它做什么
  - `INFERRED` —— 从命名、注释、类型或旁证推断,**没有直接确认**
  - `UNKNOWN` —— 无法判断

### 3. `findings.md` —— 发现

每条发现必须带:

| 字段 | 要求 |
|---|---|
| 编号 | 与 coverage 中的 `finding_ids` 对应 |
| 证据 | 文件:行号 + 代码原文,或命令 + 真实输出 |
| 证据等级 | 同上四级 |
| **证伪尝试** | **我做了什么,本可以证明这不是问题?结果是什么?** |
| 影响 | 生产上会发生什么;若不确定,写"不确定" |
| 是否属于 Codex 迁移遗留 | 是/否/不确定,并给出依据(如 git 历史) |

**没有证伪尝试的发现一律退回。** 今晚那条假警报,只要问一句"生产是不是这样调的"
就能自证。

---

## 三、必答的负面结果

报告必须含一节 `## 查过且认为无问题的`,逐项列出。

**沉默不得用于表示"没问题"。** 一个区块里若所有 item 都是 `SOUND`,
必须解释你用什么方法达成这个结论,以及**什么样的证据会推翻它**。

---

## 四、调度方的机器核验

审查方交付后,调度方按以下步骤机器核对,不通过则退回:

1. `coverage.json` 覆盖了 `enumeration.json` 的全部 item —— 逐个比对 id
2. `enumerated_by` 命令重跑一次,清单必须一致(范围没有被悄悄缩小)
3. `INFERRED` + `UNKNOWN` 占比 —— 超过三成需要说明理由
4. 抽查 3 条 `SOUND` 判定,独立复核;**任何一条站不住,整份报告退回重做**
5. 每条 finding 是否有证伪尝试

---

## 五、明确禁止

- **禁止抽样代替枚举。** 除非任务书明确要求抽样,否则"我审查了有代表性的一部分"
  等同于未完成。
- **禁止在没有跑的情况下报告执行结果。** 未跑就写 `NOT_EXAMINED`。
- **禁止用命名、注释或类型断言行为。** 那是 `INFERRED`,必须如实标注。
- **禁止只报问题不报范围。** 没有 coverage 的 findings 无法判断可信度。
- **禁止修改代码。** 本轮只审查、只记录。修复在统一计划里做。

---

## 六、给审查方的任务书模板

每份任务书必须写明:

- **已确立的事实** —— 哪些结论已验证过、不要重新推导(省 token,避免互相矛盾)
- **真相来源** —— SDK 类型 / 捕获夹具 / 数据库 / 真实 Xero / git 历史;
  **禁止依赖记忆中的文档**
- **枚举命令** —— 若调度方已知,直接给出;否则由审查方给出并写进产物
- **文件边界** —— 只读;不得提交
- **本协议路径** —— 明确要求遵守 `docs/REVIEW-PROTOCOL.md`
- **必须报告"没做什么"**

---

## 七、为什么值得这套开销

本仓库已经出厂五个同类缺陷,而闸门全绿。其中一个让"从新供应商入第一张账单"
完全不可用,**在 13 个已发布版本里存活**。原因不是没人审查,是审查的是文档
自身的一致性,而没有人被迫说清"我到底查了哪些、用什么证据"。

这套协议的全部意义,就是让这句话必须被回答。
