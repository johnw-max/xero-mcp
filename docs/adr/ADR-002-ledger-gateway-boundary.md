# ADR-002：Xero MCP 定位为账本网关；会计判断移出 MCP

状态：`PROPOSED`（取代 2026-08-18 早先的同名草案 ADR-002-jurisdiction-and-category-policy-as-data）

日期：2026-08-18

关联：不推翻 ADR-001 的分层与内核抽取方向；修正其执行现状。

## 1. 背景与前因

PRD V1（2026-08-05）的原始分工：Agent 匹配联系人、科目、税码；MCP 负责身份与
账套隔离、能力调用、风险控制、防重复和审计。

2026-08-13 的内核规格因真实质量事故（串帐、金额错误、假成功、重复写入）把科目
与税码判定收进了服务端，随之把新加坡 GST 政策、三个语义类目和 Xero 税码字面量
编译进了 MCP 核心路径。这个纠偏方向可以理解，但执行上把两类东西混在了一起：

- **不变量执行**（防串帐、防重复、防假成功、算术一致）——这部分值钱，必须留；
- **会计判断**（这笔记什么科目、什么税务处理、哪个辖区规则）——这部分把 MCP
  变成了只支持新加坡、只有三个类目的会计引擎，且违反 ADR-001 自己的抽取前置
  条件（导出物不得含 provider policy literal）。

产品处于早期，需要保持业务灵活性。会计判断的正确落点：**现在在 skill/prompt
层，将来在平台 policy 层**。MCP 回到网关本职。

## 2. 决策

**Xero MCP 是账本网关（ledger gateway）：身份与隔离、忠实读取、受核验的写入、
完整审计。不做会计判断。**

调用方（Agent，由 skill/prompt 约束）提交**显式的** Xero 原生值——科目代码、
税码、金额——MCP 对照**目标账套的真实数据**核验后执行；核验不过即拒绝。
MCP 自身不持有任何辖区规则、类目词表或税务语义映射。

## 3. 边界契约

### MCP 保证（不可外移）

1. **对的账套**：target session 钉定、租户白名单、上游 source case 与租户的
   首用即绑定。串帐防线在此。
2. **不重复**：幂等键 = 持久化 mutation ID、业务坐标预留、原生幂等恢复窗口。
3. **不假成功**：provider 回执 + 同 ID 精确回读（零容差）+ 诚实状态词表；
   聊天文字永远不构成成功证据。
4. **数字自洽**：净额+税=总额、行合计=单据合计、借贷平衡；行税额必须等于
   净额 × 所选税码在**该账套**的真实税率（按币种最小单位舍入）；币种与账套
   基础币种规则一致。
5. **真实存在**：科目、税码、联系人必须在目标账套中存在且 ACTIVE，以实时
   读取为准，不接受猜测值。
6. **权限**：OAuth scope、standing delegation、写闸、一次性写入许可。
7. **预览即执行**：case 版本 + plan hash 不可变，执行的就是预览过的。
8. **完整审计**：调用、来源、版本、回执、回读全链路可追溯。

以上 8 条全部只依赖「调用方声明了什么」和「账本实际是什么」的对照，
不需要 MCP 拥有任何会计规则。

### MCP 不做（移出）

- 判断一笔业务记什么科目、用什么税务处理；
- 辖区规则（GST 税率、免税分类、Regulation 33 之类）；
- 类目词表（咨询收入/办公用品/云订阅这类语义桶）；
- 事务所的记账习惯与科目映射。

这些**现在**由 agent-skills 里的记账 skill 承载（SG 的规则改写成 skill 内容），
**将来**由平台 policy 层以版本化制品注入 Agent。两个阶段 MCP 契约不变。

### 姿态保障

MCP 只写 DRAFT。过账、审批永远由人在 Xero 内完成。这是边界的一部分，
不是临时限制。

## 4. 对现有代码的处置

| 处置 | 内容 |
|---|---|
| **保留** | OAuth broker、target session、租户白名单、幂等+permit+业务坐标预留、回执+零容差回读、崩溃恢复、审计、case 版本+plan hash、source-case 绑定、全部读工具 |
| **降级为核验** | 税码解析器：保留「存在、ACTIVE、税率精确相符、方向正确」的账套核验；删除「语义→税码」映射决策 |
| **移出公开契约** | `accounting_category`/`tax_class` 枚举、`jurisdiction` literal、SG 政策模块。公开写入契约改收显式 `account_code` + `tax_type` + 金额；SG 知识改写为 skill |
| **简化部署** | 每租户 CoA profile env 不再是开写闸的硬前提；以账套实时 CoA 为核验依据 |
| **封存** | firm governance / exclusive-writer 机制、90-claim 治理框架（不删除，不作为发布门槛） |
| **以后** | QuickBooks 真实接入时按 ADR-001 抽共享 kernel 包；平台 policy 层成熟时 skill 内容上移 |

## 5. 诚实的代价

一笔**连贯但错误**的会计处理——金额自洽、科目真实存在、但业务上记错科目或
税务处理（例如该标准税率却整体按零税率申报）——MCP 将不再拦截。

防线转移到：skill 质量、会计师对 DRAFT 的复核、将来的平台 policy 层。
早期可接受，因为：只写 DRAFT、入账永远有人把关；且最常见的错误形态
（选错税码但金额没跟着一起错）仍会被第 4 条算术核验拦下。

不可接受的替代方案是反向的：为了拦住业务错误把辖区规则留在 MCP，
代价是每个地区、每个类目、每次规则变更都要改 MCP 发版——这正是本轮
实际发生的僵化。

## 6. 验收

- 公开写入契约不再出现任何辖区或类目词汇；
- 以显式值提交的合法 SG 单据，行为与现版本逐字节等价（route、受核验字段、回执、回读）；
- 错误科目代码 / 不存在税码 / 税率与金额不符，均以明确 reason code 拒绝且零写入;
- 现有 SG 验收场景（金额矛盾、重复、注入、崩溃恢复）全部保持通过；
- agent-skills 中出现承载 SG 记账规则的 skill 版本，与 MCP 部署解耦。

## 跨 MCP 交接：上游 case 与 Xero 组织的绑定（2026-08-19 实测）

Drive MCP（accountingv2）与本 MCP 是两套独立系统，各自有 case 概念。本 MCP
无法改动上游，能守住的边界只有一条：**同一个上游 case ref 不得落到两个 Xero
组织**。这条在 `accounting_case_source_case_bindings` 上以
`PRIMARY KEY (workspace_id, source_system, source_case_ref_hash)` 实现，
写入是单条原子 upsert——仲裁者是数据库约束本身，应用层没有"先查再写"的
竞态窗口。

对部署在线的 067 构建实测（仓库层直调，未执行任何 Xero 写入）：

| 动作 | 结果 |
|---|---|
| ref `HWB-2026-08-BILLS-03` → Demo Company (Global) | `BOUND_FIRST_USE` |
| 同一 ref → zcloak | `TENANT_CONFLICT`（拒绝） |
| 同一 ref → Demo Company 再来一次 | `BOUND_CONFIRMED`（幂等） |

冲突被拒时，返回值与 agent 看到的错误信封里都**不含**另一个租户的 id 或
名称——只有 `SOURCE_CASE_TENANT_CONFLICT` 与
`ACCOUNTING_CASE_SOURCE_CASE_BINDING`。冲突在 case 版本落库之前抛出，不留
半写状态。`case_ref` 本身只以 SHA-256 摘要存储，原文不落库也不回传。

范围说明（非缺陷）：绑定按 `workspace_id` 分域。这防的是**一个工作区内**
同一份上游材料被记进两家 Xero 组织，也就是串帐本身；两个不同工作区各自引用
同一个 ref 不在此约束内，那属于工作区隔离，是另一个问题。
